# Download speed: what limited DDM, and what changed (2026-11-27)

DDM before these changes against them, measured on the lab server (`crates/labserver`, faults
per URL) and on real servers, with curl (one connection) and aria2c 1.37.0 (`-x16 -s16`, through
its RPC) beside it (`tools/bench/others.py`). The measuring line: about 0.2 to 2.7 MiB/s, its
speed changing from minute to minute, a round trip of about 200 ms to European servers. On real
servers the line was often the limit: those numbers say what works and what doesn't more than
how fast.

## What limited DDM, and the fixes

| Found | Cause | Fix |
|---|---|---|
| An HTTP/2 server (GitHub, Google, OVH) got DDM's 8 connections as 8 streams of one TCP connection | One HTTP client for the whole download: hyper's pool shares one HTTP/2 connection per host (the earlier build had turned HTTP/2 on) | One client per connection (`Lanes`): each its own TCP connection; HTTP/2 kept, so a part cut short by a split ends its stream and the warm connection serves the next request |
| A write held up longer than 12 s cut every connection (a 1 GiB lab run on a saturated disk: all 8 cut after a 22 s wait and asked again, 39 s in all) | reqwest's read timeout runs from the last chunk read, also while the engine waits for the disk | The lanes' clients have no read timeout: the engine times the silence itself, disk waits left out (a 7.6 s wait in the final run passed without a cut) |
| A silent connection held its part for the whole read timeout (12 s) | Nothing looked at a connection that received nothing (the slowness check runs when data comes) | A connection silent 3 s (or 4 times the quickest range answer) while the others got 1 MiB since reconnects at once |
| A small file from a CDN slow to answer each connection took longer on 8 connections than on 1 (the video work: TikTok's CDN answers in 1.3 s; 1.3 MB took 3.7 s on 8, 1.6 s on 1) | Every connection opened at once, whatever the file's size | A file up to 16 MiB starts on its first connection; after half its time to first byte (50-400 ms) the others open if it wouldn't finish within two of its times to first byte, as many as the rest needs (a Metalink download's mirrors are still asked from the start) |
| Splits near the end cost requests (and, over HTTP/1.1, the shortened connection) for halves that would have come sooner where they were | Splits went down to 12 KiB whatever the speed | No split leaves a half smaller than what a connection receives while a request waits for its answer |
| A server without ranges (Cloudflare's speed test) got 7 range requests answered with the whole file at the start | All connections opened before ranges were known | Without `Accept-Ranges: bytes` in the first answer, one range request asks first |
| Hetzner's speed servers (fsn1, ash): no byte in 12 s, the download failed | They hang up, unanswered, on a browser's User-Agent from a connection that isn't a browser's (Chrome's, Firefox's and IE 11's names alike; curl's and DDM's own served) | The first request hung up on is asked once more by DDM's own name (`DannexDownloadManager/<version>`), kept for the resume; a User-Agent the user set stays |
| proof.ovh.net: 2 to 4 of 8 connections | The server answers 429 Too Many Requests beyond a few connections from one address, and stops answering it for minutes after a burst (two quick runs of 8 were enough) | Not DDM's to change: DDM learns the cap (now on the command line too, which had no table) and retires the refused connections instead of retrying them |
| The command line took 0.6 s for a 256 KiB file | It looked at the download every 500 ms | It looks every 25 ms (progress still every 500 ms) |

Kept as they were, measured: 8 connections by default (more only help a server that caps each one
and allows them); per-connection slow start is TCP's (lanes keep connections warm over HTTP/2);
DNS goes through the system's cache, the address race's winner is remembered for 5 minutes, and
the lanes share one resolver, so a DNS chosen in Options isn't set up again for each connection;
TLS 1.3 needs one round trip with or without resumption, so lanes don't share sessions; buffers (256 KiB a
connection, a write at least every second) were not the limit on the lab's 1 GiB run; HTTP/3:
see [Appendix A](#appendix-a-http3-an-evaluation).

Read with it:

- **Stalls**: The earlier build waited out its 12 s read timeout on each silent response; aria2c waits out its
  60 s timeout; curl hangs. Now a silent connection reconnects after 3 s.
- **Small files**: the command line no longer waits for its next half-second look; and a file
  that comes at once stays on one connection (256 KiB: 1 request instead of 4, the bytes the
  server sent 1.00× the file instead of 2.00×). curl's and aria2c's 31 ms are a process that
  starts in 20 ms and a daemon that is already running; DDM's command line is the app's
  program (about 100 ms to start).
- **Requests**: the split floor ends the shower of tiny splits at the end (1 GiB: 10 requests
  instead of 17, and 11 instead of 26 in the focused run; 100 MiB with 150 ms latency: 8
  instead of 27; a server that allows 2 connections: 15 instead of 47).
- **aria2c's 16 connections** win where the server caps each connection (2 MB/s each: 16 × 2
  against 8 × 2); DDM at 16 wasn't run here. DDM's default stays 8 (Options → Connection takes
  up to 32, or 128): a cap per connection is the one case more help, and most servers allow
  fewer from one address (OVH and Hetzner above).
- **1 GiB**: the disk, not the network: the transfer took the same in both (837 against 845 ms
  median); two of the change's four runs waited for the disk (7.6 s in the transfer, 3.6 s for
  the final flush), as curl and aria2c each did once. A focused run, 8 each, the two DDMs
  alternating ([Appendix B2](#b2-the-focused-1-gib-run)): before 3723 ms (1898–8557), now 3069
  (1726–6978); the disk was then busier for both.
- **One crawling connection in three** (32 MiB): within the runs' spread (3671–4774 against
  3764–4398). The ramp then applied to files up to 32 MiB and delayed the others by 50 ms; it
  now applies up to 16 MiB only, so a 32 MiB file opens all its connections at once as before.

## Not verified

- The app (its list, its progress window) was not run: the command line drives the same engine.
- macOS and Linux: built and tested on Windows only (the change is portable Rust).
- A lossy mobile or satellite line, HDDs and network shares: the disk-wait fix was measured on a
  saturated SSD only.

## Appendix A: HTTP/3, an evaluation

**Verdict: not now.** DDM's HTTP stack can't do HTTP/3 in a release build without unstable
upstream code, and on the measured line HTTP/3 brought nothing that DDM's separate connections
don't already get. What would change that is listed at the end of this appendix.

### What DDM's stack can do

| Client | Used for | HTTP/3 |
|---|---|---|
| reqwest 0.13 (hyper 1, rustls) | every download, the first request, ranges | Only behind `RUSTFLAGS="--cfg reqwest_unstable"` and its `http3` feature (h3 0.0.8 and h3-quinn 0.0.10 over quinn 0.11): a flag for the whole build, which reqwest's authors mark as unstable and may change in any release |
| hyper 1 | under reqwest | No HTTP/3 of its own |
| wreq 0.16 (BoringSSL, the browser-like connection, #668) | sites whose bot check refuses DDM's own connection | HTTP/1.1 and HTTP/2 only |

Besides the client, HTTP/3 would need in DDM:

- **Finding it.** A server offers HTTP/3 in an `Alt-Svc` header or a DNS HTTPS record; the first
  connection is TCP, and each later one would have to remember the offer (per host, with its
  lifetime).
- **Falling back.** QUIC is UDP: some networks block or throttle it, so every HTTP/3 attempt needs
  a quick fall-back to TCP (browsers race them).
- **The network adapter and its kill switch (#35).** `net.rs` binds DDM's TCP connections to the
  chosen adapter; QUIC's UDP sockets would need the same binding and the same checks.
- **Proxies.** HTTP proxies (CONNECT) and SOCKS5 without UDP can't carry QUIC: through a proxy,
  downloads stay on TCP.
- **Several connections.** Like HTTP/2, one QUIC connection carries all its streams under one
  congestion controller: a download needs one QUIC connection per lane, as DDM now opens one TCP
  connection per lane (measured below: 8 streams on one QUIC connection were the slowest).

### What was measured

A scratch program on the same reqwest 0.13.5 (built with `--cfg reqwest_unstable`), each mode
downloading ranges of Google's 175 MB Chrome installer
(`dl.google.com/.../googlechromestandaloneenterprise64.msi`, which offers `h3` in `Alt-Svc`) for
10 s, modes in rotating order, 3 rounds; MiB/s, median (each round). The line: about 0.5 to 2.7
MiB/s, with a round trip of about 200 ms to European servers; its speed changed between rounds,
so only differences within a round mean something.

One connection:

| HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|
| 0.32 (0.45, 0.29, 0.32) | 0.62 (0.77, 0.62, 0.44) | 0.69 (0.88, 0.69, 0.59) |

Eight ranges at once, a faster hour (round medians of 3):

| HTTP/2, 8 streams on 1 TCP connection | HTTP/1.1, 8 TCP connections | HTTP/2, 8 TCP connections | HTTP/3, 8 streams on 1 QUIC connection |
|---|---|---|---|
| 1.88 | 2.15 | 2.50 | 2.31 |

Eight ranges at once, a slower hour:

| HTTP/1.1, 8 TCP connections | HTTP/2, 8 TCP connections | HTTP/3, 8 streams on 1 QUIC connection | HTTP/3, 8 QUIC connections |
|---|---|---|---|
| 0.49 (0.50, 0.49, 0.27) | 0.61 (0.73, 0.49, 0.61) | 0.24 (0.22, 0.24, 0.59) | 0.80 (0.86, 0.80, 0.63) |

Cloudflare's speed test (`speed.cloudflare.com/__down`) doesn't speak HTTP/3 (the QUIC handshake
ends with TLS alert 40), nor HTTP/2 over TCP, nor ranges; it refuses more than 100 MB a request.

What it says:

- On one connection HTTP/3 was a little faster than HTTP/2 here (one round trip less to open,
  loss recovered per stream), and both well ahead of HTTP/1.1 on Google's servers.
- With 8 connections the line was the limit: HTTP/1.1, HTTP/2 and HTTP/3 on separate connections
  were within the line's own variation of each other.
- Multiplexing is what costs: 8 streams on one connection (HTTP/2 or HTTP/3) were the slowest in
  both hours. That, not HTTP/3, was worth fixing: DDM before these changes carried an HTTP/2 server's 8
  connections over one TCP connection; each connection now has its own (`Lanes`, see
  [What limited DDM, and the fixes](#what-limited-ddm-and-the-fixes)).

### What would make it worth doing

- reqwest's HTTP/3 out of `reqwest_unstable` (or hyper with HTTP/3), with h3 past 0.0.x.
- A measurement where HTTP/3 on DDM's connections beats TCP on them: a lossy line (mobile,
  satellite) where TCP's loss recovery is the limit, not the line's speed.
- Then: Alt-Svc / HTTPS-record discovery per host, a raced fall-back to TCP, QUIC sockets bound
  to the chosen adapter, TCP through proxies, one QUIC connection per lane; a lab server speaking
  HTTP/3 (quinn) with per-connection caps and loss, for the tests.
