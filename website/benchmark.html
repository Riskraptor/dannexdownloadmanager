The new engine

In November 2026 we looked for what slowed DDM down, on the lab server and on real servers, beside curl and aria2c, and changed the engine. What the clock said:

How we tested

  • Server. The lab server from this repository, on 127.0.0.1, serving generated content. It throttles, delays, refuses or cuts connections per test, and logs every request with millisecond start and end times.
  • Programs. IDM and DDM, both at default settings (8 connections), each given the download through the same documented command line: /d URL /p folder /f name /n. Both save to the drive that holds IDM's temporary folder, so neither pays a cross-drive copy.
  • Timing. End to end: from issuing the command to the finished file under its final name, polled every millisecond on a monotonic clock. DDM renames its finished file into place; IDM creates the final file early and fills it, so for IDM the moment it reaches full size counts. Transfer: the server's first request to its last byte, read on the same clock through a calibration request before each run.
  • Fairness. The programs alternate, IDM first on even runs and DDM first on odd ones, so drift on the machine hits both. One warm-up run each is discarded. Failed runs are counted, not dropped. Before every run the harness waits until the loopback is quiet: against a server that refuses extra connections IDM retries about 250 times a second, leaving thousands of closed sockets for half a minute; without the wait, whichever program ran next was timed on that backlog.
  • Statistics. Medians with interquartile ranges, bootstrap 95% intervals (10,000 resamples) for each median and for the ratio of medians, and a two-sided Mann–Whitney U test.
  • Limits. A loopback link has no real distance or packet loss; the faults stand in for them. Results are from one machine. Run it yourself: python tools/bench/bench.py, then python tools/bench/report.py.
